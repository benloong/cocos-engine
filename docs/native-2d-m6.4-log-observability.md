# M6.4 Windows 日志可见性与验收观测

> 2026-11-17。修复重定向 stdout 中完成标记被缓存的问题，保留完整运行证据。数据见 [验收记录](./native-2d-m6.4-log-observability-results.json)。

## 问题与确定性证据

M5 之前曾两次在 45 秒窗口内缺失完成标记。新诊断保留了修复前 3 次完整运行：进程仍存活，墙钟与单调计时一致，但日志时间戳与文件可见时间的粗略差为 5.10、4.67、1.64 秒。Win32 Log::logMessage 使用 wprintf(stdout)，没有刷新重定向 stdout。旧两次失败没有留存完整 stdout 和退出码，不能把它们逐例宣称为崩溃或确定的调度故障。

新增真实 C++ 日志子模式：强制 stdout 全缓冲，调用 Kernel/Script 两种生产日志入口，然后创建 ready 文件并等待父进程 release。ready 证明日志调用已返回；父进程在 child 仍存活时要求两个标记均可见。修复前该断言确定性失败，而正常退出后两个标记都出现，exit=0。该结果区分了“未执行”和“执行后仍缓存”，不依赖渲染器、后续日志或延长睡眠。

## 修复与观测入口

Win32 日志在 wprintf 后 fflush(stdout)，随后恢复控制台颜色，其他平台路径保持原代码。没有迁移非 2D 功能或增加渲染调用；仅修正本次构建/验收必要的日志支持。stdout 仍由 CRT 拥有，代码仅借用/刷新；测试的 ready 输出流在局部作用域关闭。没有新增 shared_ptr。

M5 入口保留原 45 秒预算和全部像素/样式/hit/miss 断言，改用每次唯一的工作区 stdout/stderr 与 JSON 报告。报告记录 app SHA256、单调/墙钟、CPU、进程状态、退出前结果和阶段时间线；exitBeforeCleanup 与 killedForCleanup 分开，失败也保留资料。原生子进程可见性测试已接入 M0，Log.cpp 加入 native 源码审计指纹。

## 验收

按统一文档重建 cocos-m1-test、override、资源和 Windows Debug app。完整串行 M0→M2/M3→M4→M4 extra→M5→UV→定向 Jest 一次通过，M0 也包含应用 M2/M3 和新增日志子进程门禁。M0 末尾 8 suite/33 tests、定向 6 suite/32 tests、UV 1 项通过。12 份 Web/native 原始 RGBA 的 SHA256 相同，最大通道差值 0。

同一修复后二进制连续 3 次 M5 无重试通过，耗时 27.11、27.52、27.01 秒；标记时间戳到文件观测的粗略差为 0.57、0.50、0.67 秒。日志只有秒精度，不能把该值当精确时延或 2D 性能收益。预算未增加，样式与命中断言未放宽。

本轮关闭可确定复现的 Windows stdout 可见性缺陷。旧两次缺失缺少逐例资料，证据仅支持缓冲问题能解释该类现象；完整长期调度/资源回收、1000 次加载、线程和全平台稳定性仍按 M6 计划验收。工作区原有六份测试入口 cwd 修正未并入本提交，其哈希继续随验收记录保留。
